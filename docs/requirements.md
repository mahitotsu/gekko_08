# 要件定義

参照実装を設計する前提となる要件をまとめる。

元にした文書：[PRFAQ](prfaq/aws-authorization-context-propagation.md)

## 目的と対象

- AWS上でマイクロサービスを実装するエンジニアに向けて、Authorization ContextとWorkload Identityを分離し、
  「誰の権限で処理するのか」を多段呼び出しの奥まで届ける仕組みの参照実装（OSSのCDK構成と設計ガイド）を提供する。
- 事業化はしない。サポートやSLAは提供しない。

## 機能要件

| ID | 要件 |
|---|---|
| FR-1 | 各ホップは、受け取ったリクエストについて次の4つを確かめられる。(a) 誰の代理か（ユーザーの識別子）、(b) どのサービスから来たか、(c) 自分宛てか、(d) 委任の範囲（このリクエストの目的と、呼び出し元に許された操作）。OAuth Token Exchangeと同等のことを実現する |
| FR-2 | 認可判定は、各ホップのアプリが、検証済みの委任の範囲と、権威あるデータ源から得た業務上のアクセス権の両方を使って行う。ヘッダー・引数・自然言語による自己申告は使わない |
| FR-3 | ユーザーの識別子とリクエストの目的は入口で確定し、途中のホップ（AIエージェントを含む）は変更も拡大もできない。業務上のアクセス権は権威あるデータ源から得て、途中のホップは変更できない |
| FR-4 | 途中のホップを飛ばして、その先のホップを呼ぶことはできない |
| FR-5 | ブラウザなどのパブリッククライアントには、認証情報（IdPのトークン、AWSの認証情報）を持たせない |
| FR-6 | 各ホップの処理を、元のユーザーとリクエストに結びつけて追跡できる。リクエストを識別する値は入口で決まり、途中のホップは変えられない |
| FR-7 | デモとして、同期のマイクロサービスの多段呼び出しに加えて、AIエージェント→MCPサーバー→内部サービスのシナリオを含める。次のことを示す。(a) プロンプトインジェクションで誘導されたエージェントの要求が拒否される。(b) リクエストの目的によって許す範囲が変わる。特に、エージェントを経由しない、人間の操作によるリクエストでだけ実行できる操作があり、エージェントによるリクエストからは、エージェントのホップが侵害されても実行できない。(c) 業務上のアクセス権の変更が反映される。(d) 監査の画面で、1回のリクエストについて、各ホップが記録した認可の根拠（誰の代理か、呼び出し元、リクエストの目的、scope）を、AWSが記録した事実と突き合わせて示す。監査も他のホップと同じ仕組みで守り、監査の権限を持つユーザーだけが使える |
| FR-8 | 業務上のアクセス権の変更（異動など）は、次のリクエストから反映される |

## 非機能要件

| ID | 要件 |
|---|---|
| NFR-1 | サーバーレスとマネージドサービスを最大限に使い、コストと運用負荷を下げる |
| NFR-2 | 認可サーバー、SPIRE、サイドカーなどの常駐コンポーネントを持たない |
| NFR-3 | レイテンシの目標値は置かない。ホップごとの追加時間を実測して公開する |
| NFR-4 | 利用者が`cdk deploy`で自分のAWSアカウントに再現できる |

## セキュリティ要件

| ID | 要件 |
|---|---|
| SR-1 | ホップ間で受け渡す認証情報が漏れても、それだけではどのホップも呼べない |
| SR-2 | 同じアカウント内の他の主体（広い権限を持つものを含む）が、許可されていないホップを呼べない |
| SR-3 | 認証情報を、ログ・トレース・エージェントのLLMのコンテキストに入れない |

## 前提と範囲

| 項目 | 初版の範囲 |
|---|---|
| 呼び出し方式 | 同期呼び出しだけ |
| 処理時間 | 1回のリクエストの処理は、各ホップで15分以内に収まる。長い対話は複数のリクエストとして扱う |
| アカウント | 単一のAWSアカウント |
| 連携先 | AWS内部のホップ間だけ。AWSの外のサービスにユーザーの証明を渡すことは扱わない |
| コンピュート | ホップはAWS Lambda（Function URL） |
| IdP | Amazon Cognito User Pool（Pre Token Generation V2） |
| リージョン | ap-northeast-1（デモのエージェントが、日本国内の推論プロファイルでモデルを呼ぶため） |

## 将来の拡張（初版では扱わない）

- 非同期処理（SQS・EventBridgeなど）を挟む呼び出し
- 複数のAWSアカウントにまたがる構成
- AWSの外のサービスへのユーザーの証明の受け渡し（AgentCore Identityなど既存の手段との使い分けを含む）
- 利用者のサービスの実装言語を問わず、共通部品の機能を使えるようにする
- API Gateway（REST API）を経由してホップを呼べるようにする（WAF、スロットリング、プライベートAPIを使う既存のシステムへの当てはめ）
- 各ホップの認可判定をポリシー言語（Cedar）で書けるようにする（Amazon Verified Permissionsへの問い合わせ、または関数の中での評価）。判定の入力には、検証済みの値と権威あるデータ源から得たアクセス権を使う

## スコープ外

- 業務RBACの持たせ方の一般論（参照実装では1つの例を示すにとどめる）
- ユーザーの権限でAWSリソースに直接アクセスすること
- Lambda以外のコンピュート（ECSなど）
- Cognito以外のIdPでの検証
- Pre Token Generation V1トリガー
