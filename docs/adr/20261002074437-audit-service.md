# ADR: 監査サービスと監査の画面で、ホップの記録とAWSの記録を突き合わせる

## Status

Accepted (2026-10-02)。要件の変更（FR-7に(d)を加える）とあわせて合意した。
[デモのADR](20261001123029-demo-account-unfreeze.md)の「gekko_07の構成を丸ごと取り込む」を採らなかった判断は変えない。取り込むのは、記録を突き合わせる考え方だけである。

## Context

デモの画面は、操作ごとに、bffが刻んだ取引の目的と結果、拒否した層を示す（[画面のADR](20261002065842-demo-ui-react-static.md)）。各ホップが実際に何を検証して判定したか
（誰の代理か、呼び出し元、目的、scope）は見えない。

各ホップが検証した値を応答で上流へ運べば表示はできるが、下流の値は途中のホップを経由するので、そのホップが侵害されれば偽れる。
表示の手段としては働いても、「IAMが強制した」ことの裏付けにはならない。

一方、AWSの側には、ホップが書き換えられない記録がある。CloudTrailの`GetWebIdentityToken`のイベントには、呼んだ主体（chain用roleのセッション）、
宛先（`audience`）、scope（`tags`）、ユーザー（`sessionContext.sourceIdentity`）が残り、bffの`AssumeRole`のイベントには取引の目的（`tags`）が残る。
bffは、chainとJWTの発行の`RoleSessionName`をリクエストIDにしているので、1回の取引のイベントをリクエストIDで引ける。各ホップのログ（アプリの自己申告）とこれを
突き合わせれば、ログに書かれた目的とscopeが、STSが実際に発行したJWTと一致するかを確かめられる。今はこの突き合わせを手で行うしかない。

gekko_07のaudit-serviceは、業務の自己申告の記録と第三者の記録（IdPのイベントログ）をトークンの識別子で突き合わせていた。同じ構図を、この参照実装の
記録（ホップのログとCloudTrail）で作れる。

## Decision

**監査サービス（audit-service）を、他のホップと同じ仕組みで守るホップとして加える。監査の画面から、1回の取引について、各ホップのログ（自己申告）と
CloudTrail（AWSの記録）を、リクエストIDで突き合わせて示す。監査できるのは、監査の権限を持つユーザーだけにする。**

1. **ホップとしての位置**：bff → audit-service → entitlement-service。bffは新しい目的`audit`を刻み、scope`audit:read`でaudit-serviceを呼ぶ。
   audit-serviceは、属性サービスから得た業務的なアクセス権に`audit:view`があるときだけ応じる。`audit:read`は目的に縛らない
   （利用側はbffだけで、ほかのホップは宣言していないので呼べない。[委任の範囲の定義のADR](20261001130745-delegation-definitions.md)）。
2. **監査の権限**：権限マスタに役職「監査担当」（`audit:view`だけ）を加え、デモのユーザーsuzuki（本部・監査担当）を足す。監査担当は凍結の解除も案件の参照もできず、
   支店長と担当者は監査できない。どちらの拒否も、業務的なアクセス権の層で起きる。監査担当は、支店を問わずすべての取引を監査できる。
3. **できること**：
   - **最近の取引の一覧**：bffのログ（`handled`）から、期間内の取引（時刻、ユーザー、経路、目的、結果、リクエストID）を新しい順に返す。
   - **1回の取引の突き合わせ**：リクエストIDを受け取り、次の2つを集めて突き合わせる。
     - ホップの記録：各ホップのログの`handled`と`rejected`（ホップ、呼び出し元、ユーザー、目的、scope、結果）。Logs Insightsで引く。
     - AWSの記録：CloudTrailの`LookupEvents`（`Username`＝リクエストID）で得る`AssumeRoleWithWebIdentity`、`AssumeRole`、`GetWebIdentityToken`。
     - ホップの記録の1行ごとに、対応する`GetWebIdentityToken`（呼んだ主体が呼び出し元のchain用role、`audience`がそのホップ、`tags`のscopeと
       `sourceIdentity`が一致）があるかを判定し、「一致」「不一致」「AWSの記録が未着」のどれかを付ける。目的は、bffの`AssumeRole`の`tags`と、各ホップの記録の目的が一致するかで判定する。
4. **返す値**：突き合わせに使う項目だけを、名前を決めて取り出して返す。CloudTrailのイベントをそのまま返さない（`responseElements`に認証情報の一部が入りうる。SR-3）。
   roleのARNは、CDKが渡す対応表でホップ名に置き換え、アカウントIDを画面に出さない。
5. **画面**：結果のカードに「監査で確かめる」を置き、リクエストIDを渡して監査の画面を開く。監査の画面は、取引の一覧と、選んだ取引の突き合わせの表を示す。
   CloudTrailの記録が未着のときはその旨を示し、再確認できるようにする。
6. **権限**：audit-serviceの実行roleに、`cloudtrail:LookupEvents`と、各ホップのロググループに限った`logs:StartQuery`・`logs:GetQueryResults`を与える。

## 採用しなかった選択肢

- **各ホップが検証した値を、共通部品が応答のヘッダーで上流へ運ぶ**：すぐに表示できるが、途中のホップが侵害されれば下流の値を偽れる。監査があれば、
  同じ値をより信頼できる出どころで見せられる。表示のためだけに共通部品を変えることにもなる。
- **トレース（Transaction Search）を突き合わせに使う**：スパンの属性はホップの記録で、ログと同じく自己申告である。AWSの記録としてはCloudTrailを使う。
  トレースは、ログの`traceId`から開けるので、画面からのリンクにとどめる。
- **支店長に監査の権限を足す**：ユーザーは増えないが、操作した本人とは別の人が監査する、という業務の分担と、権限が操作ごとに分かれていることを見せられない。
- **gekko_07のように、業務のデータ（提案と実行の記録）とIdPのイベントを突き合わせる**：この参照実装には提案の記録がなく、IdPは呼び出しごとのトークンを発行しない。
  ホップごとの委任の記録は、STS（CloudTrail）にある。
- **CloudTrail LakeやAthenaを使う**：`sourceIdentity`でも引けるが、イベントデータストアやテーブルの用意が要り、固定費や手順が増える。リクエストIDで引くなら`LookupEvents`で足りる。

## Consequences

### よくなること

- 「IAMが強制した」ことを、「AWSがそう記録している」まで、画面で示せる。ログに書かれた目的とscopeが、STSが発行したJWTの記録と一致することを、
  取引ごとに確かめられる。
- 監査という影響の大きい読み取りにも、同じ仕組み（目的、scope、業務的なアクセス権）が当てはまる例になる。
- 手で行っていた突き合わせが、画面とコードで再現できる形になる。

### 引き受けること

- **CloudTrailの遅れ**：イベントが`LookupEvents`で引けるまで、最大15分ほどかかる。直後の取引は「AWSの記録が未着」になる。
- **リクエストIDはSTSもIAMも強制しない**：侵害されたホップが`RoleSessionName`を別の値にすると、そのホップのイベントはリクエストIDでは引けず、「未着」と区別できない。
  監査の画面が示すのは、リクエストIDで引ける範囲の突き合わせである。ホップの侵害を疑うときは、`sourceIdentity`と目的で引く（CloudTrail Lake、Athena）。
- **audit-serviceの権限が広い**：アカウントのCloudTrailのイベント履歴と、各ホップのログを読める。侵害されると、すべてのユーザーの取引の記録が読まれる。侵害された要素ごとの影響の説明に加える。
- **`LookupEvents`の上限**：アカウント・リージョンごとに毎秒2件。監査の画面の利用には足りる。
- **Logs Insightsの費用と時間**：照会ごとにスキャンしたデータ量で課金され、結果まで数秒かかる。照会の期間を限る。
- **デモの準備**：ユーザーsuzukiを作る手順がREADMEに増える。
