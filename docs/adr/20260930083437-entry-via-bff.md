# ADR: 入口はBFFとし、ブラウザには認証情報を持たせない

## Status

Accepted (2026-09-30)

## Context

[多段伝播のADR](20260930064314-multi-hop-authorization-context-propagation.md)では、ログイン時に`AssumeRoleWithWebIdentity`で
Authorization Context（SourceIdentityとtransitive session tags）をSTSセッションへ刻み、そのセッションを起点に各ホップへ伝える構成を決めた。
入口（Frontend→最初のホップ）をどこで扱うかは未解決として残した。

論点は、Cognitoのトークンを受け取って`AssumeRoleWithWebIdentity`を呼び、最初のホップを呼ぶ主体をどこに置くかである。

- **ブラウザで行う**：ブラウザがCognitoのトークンと、aliceの属性を持つSTSセッション（`AccessKeyId`・`SecretAccessKey`・`SessionToken`）を持つ。
- **BFF（Backend for Frontend）で行う**：サーバー側の入口がこれらを持ち、ブラウザには持たせない。

ブラウザはパブリッククライアントであり、秘密を安全に保持できない。XSSや拡張機能、端末の共有などで、JavaScriptから読める値は持ち出されうる。
さらに多段伝播のADRでは、最初のホップの入口で呼び出し元の実行role（actor）を確かめる。ブラウザには実行roleがないため、ブラウザを最初の
呼び出し元にすると、この確認ができない。

## Decision

**入口はBFFとし、ブラウザのようなパブリッククライアントには認証情報を持たせない。**

1. BFFはCognito User Poolのコンフィデンシャルクライアントとしてログインを扱い、Cognitoのトークンはサーバー側でだけ保持する。
2. `AssumeRoleWithWebIdentity`はBFFが呼ぶ。aliceの属性を持つSTSセッションはBFFの中にだけ存在し、ブラウザには渡さない。
3. BFFは多段呼び出しの最初の呼び出し元（ホップ）になる。最初のホップの入口は、BFFの実行roleだけを許可し、BFFが発行したJWT
   （`aud`＝最初のホップ）を検証する。以降は多段伝播のADRと同じ。
4. ブラウザとBFFの間は、JavaScriptから読めないセッション（HttpOnly・Secure・SameSiteのcookieなど）で結ぶ。

## Consequences

### よくなること

- ブラウザからは、Cognitoのトークンも、aliceの属性を持つSTSセッションも持ち出せない。
- 最初のホップでも、他のホップと同じく実行role（actor）とJWT（subject、aud）の両方を確かめられる。入口だけの例外がなくなる。
- ブラウザ側のコードは、AWSの認証情報やSigV4署名を扱わない。

### 引き受けること

- **BFFという構成要素が増える**。BFFはインターネットに公開されるので、入口の認証はIAMではなく、BFF自身のセッションで行う
  （Function URLの`AWS_IAM`認証はブラウザから使えない）。
- **サーバー側でセッションとトークンを保持する**。保存先、暗号化、有効期限、リフレッシュトークンによる更新を設計する必要がある。
- **cookieを使う場合のCSRF対策**が必要になる。
- BFFが侵害されると、そこでログイン中のユーザーの権限が使われうる。BFFは最も価値の高い構成要素になる。

### 未解決（後続の設計で扱う）

- BFFのホスティング（Lambda Function URL、API Gateway、CloudFrontとの組み合わせなど）。
- セッションとトークンの保存先（DynamoDBなど）と暗号化の方法。
- `AssumeRoleWithWebIdentity`をリクエストごとに呼ぶか、IDトークンの有効期限の範囲でセッションを再利用するか。
- ログインフロー（Authorization Code＋PKCE）の実装と、Cognitoのアプリクライアントの設定（クライアントシークレットの扱い）。
