# ADR: デモのエージェントをClaude Agent SDKで作り、MCPは関数の中の中継から共通部品で呼ぶ

## Status

Accepted (2026-10-01)。[エージェントとMCPのADR](20260930093746-agent-and-mcp-on-lambda.md)の決定1を置き換える。

## Context

[エージェントとMCPのADR](20260930093746-agent-and-mcp-on-lambda.md)では、fraud-agentを、BedrockのConverse APIで書いた
最小限のツール呼び出しのループにした。デモの目的（判断が揺らいでも権限の境界は揺らがない）にはこれで足りる。
一方で、実際のエージェントはフレームワークで作ることが多い。フレームワークで作っても同じ境界を保てることを本体で示せないと、
参照実装の実用性に説得力がない。フレームワークによってOTelの出力の形式も変わるので、トレースの計装を作る前に決める必要がある。

[フレームワークへの当てはめの検証](../../experiments/agent-frameworks/RESULTS.md)で、Strands Agents（TypeScript）と
Claude Agent SDK（TypeScript）を比べ、次のことを確かめた。

- どちらでも、MCPの呼び出しを共通部品に通せ、誘導されたエージェントの要求は本体と同じく拒否された（FR-1〜4、FR-7）。ログに認証情報は出なかった（SR-3）。
- Claude Agent SDKは、Claude Codeを子プロセスとして起動する。SDKのHTTPのMCPには固定のヘッダーしか付けられないので、
  親のプロセスに中継のMCPサーバーを置いた。中継を`127.0.0.1`のHTTPにすると、Claude Codeが`traceparent`を付け、
  ホップのスパンからfraud-mcpへの呼び出しまで、トレースの親子関係が一続きになった。
- Claude Agent SDKは、成果物が展開後247.8MB（Lambdaのzipの上限は250MiB）、最大メモリが約500MBで、Strandsより重い。
- Strandsは同じプロセスで動き、軽く、OTelの標準の形式で出す。ただし、プロジェクトオーナーの判断では、利用の広がりと知名度が低く、
  読者に「実際に使われているフレームワークで動く」と示す題材として弱い。

## Decision

**fraud-agentを、Claude Agent SDK（TypeScript）で作り直す。MCPは、関数の中の中継から共通部品で呼ぶ。**

1. **エージェント**：fraud-agentのLambdaの中で、Claude Agent SDKがClaude Code（linux-arm64の実行ファイル）を子プロセスとして起動する。
   モデルは今と同じClaude Haiku 4.5（Bedrock、日本国内の推論プロファイル）。
2. **MCPの中継**：親のプロセスが`127.0.0.1`で受けるMCPサーバー（HTTP、ステートレス、JSONで応答）を立て、Claude Codeにはそれだけを
   MCPサーバーとして見せる。中継はMCPのメッセージをfraud-mcpへそのまま転送し、認可の判断はしない。
   中継は自分のスパンを作らない。受け取った`traceparent`をその時点のコンテキストにして転送し、共通部品の送信のスパンを
   Claude Codeのツールのスパンの子にする。fraud-mcpには、送信のスパンの`traceparent`を送る。
3. **共通部品が提供するもの**：MCPの通信路（`call`で送るMCPの`Transport`）と、`127.0.0.1`の中継を、共通部品の一部として提供する。
   MCPクライアントを差し替えられるフレームワークは通信路を直接使い（直接型）、できないフレームワークは中継を使う（中継型）。
4. **子プロセスに渡すもの**：認証情報（受け取ったJWT、受け渡されたセッション、chainのセッション）は親のプロセスにとどめ、子プロセスには渡さない。
   子プロセスには、**Bedrockのモデルの呼び出しだけを許すrole**の一時的な認証情報を渡す。ホップの実行roleの認証情報は渡さない。
   あわせて、組み込みのツール（Bash、Readなど）を無効にし、中継のツールだけを許し、設定ファイルを読まず、セッションを保存しない。
   Anthropicへの必須でない通信と自動更新を止める。
5. **成果物**：zipで、実行ファイルを関数に同梱する。SDKの版は固定する。合成のときに成果物の大きさを確かめ、zipの上限に近づいたら失敗させる。
   そのときは、コンテナイメージ（上限10GB）に切り替える。今zipにするのは、デプロイする人にDockerが要らず、他のホップと同じ作りで済むためである。
6. **関数の設定**：メモリは1024MB、タイムアウトは今と同じ55秒。
7. 今の最小限のループと、Strandsで作ったものは、検証記録に残し、本体からは外す。

[エージェントとMCPのADR](20260930093746-agent-and-mcp-on-lambda.md)の決定1（LambdaでConverse APIを回す）は、この決定で置き換わる。
決定2（MCPサーバーもLambdaのホップとし、入口は他のホップと同じ）は変わらない。

## 採用しなかった選択肢

- **今の最小限のループのまま**：依存が最も少ないが、フレームワークで作っても同じ境界を保てることを本体で示せない。
- **Strands Agents**：軽く、同じプロセスで動き、OTelの標準の形式で出す。通信路を渡すだけで済む。題材としての知名度の点で採らない。
  当てはめ方（直接型）は、検証記録と設計ガイドで示す。
- **両方を本体に載せる**：2つの型を動く形で見せられるが、OTelの形式が2系統になり、成果物と保守が重くなる。
- **中継をSDKの`sdk`型（子プロセスとの標準入出力）にする**：HTTPのサーバーが要らないが、子プロセスからトレースのコンテキストが届かず、
  ホップの送信のスパンがツールのスパンの子にならない。
- **子プロセスに実行roleの認証情報をそのまま渡す**：検証ではこの形で動かした。実行roleは、呼び出し先のホップの入口で呼び出し元として
  許されている。JWTがなければ呼び出し先は拒否するが、モデルの判断で動くプロセスには、Bedrockの呼び出しに要る以上の権限を持たせない。

## Consequences

### よくなること

- 実際に広く使われているエージェントの実装で、権限の境界が保てることを本体で示せる。
- 中継型の当てはめ方（MCPクライアントを差し替えられないフレームワーク）を、動く形で示せる。直接型は通信路を渡すだけなので、文書で足りる。
- トレースの親子関係が、ホップ → Claude Code → 中継 → fraud-mcpまで一続きになる。Claude Codeは本文を既定で記録しない。

### 引き受けること

- **成果物がzipの上限に近い**。余裕は約14MBで、SDKの版を上げて超えたら、コンテナイメージに切り替える。切り替えると、
  デプロイする人にDockerが要るようになる。
- **重く、遅い**。メモリは約500MB、処理時間は最小限のループやStrandsより数秒長い。処理時間の大半はモデルの呼び出しである。
- **Claude Codeのテレメトリは独自の形式（`claude_code.*`）で、SigV4の署名ができない**。収集先へは関数の中の受け口を経由させる必要がある
  （[送り方のADR](20261001053646-telemetry-direct-export.md)の決定3で、親のプロセスが受けて署名して転送することにした）。
- **子プロセスの振る舞いは、Claude Codeの実装に依る**。組み込みのツールの無効化、必須でない通信の停止などは設定で行うので、
  SDKの版を上げたときに、シナリオテストと観測で確かめ直す。
- **利用条件**：Claude Agent SDKとClaude Codeは、Anthropic PBCのプロプライエタリなソフトウェアで、
  [Anthropicの条件](https://code.claude.com/docs/en/legal-and-compliance)に従う（2026-10-01に確かめた）。Bedrock経由では、利用者の既存の商用契約が適用される。
  参照実装は実行ファイルを配らず、合成のときに取得して改変せずに入れるので、公開には支障がない。ただし、自分の組織の利用者のために
  自分の認証情報で動かす使い方は認められる一方、社外の利用者に代わってClaudeの利用料を払う・転売する・仲介することは、
  個別の合意がない限り認められない。利用者がデモの形を社外向けのサービスに転用するときの制約になる。
- **Bedrock用のroleが1つ増える**。親のプロセスは、実行環境ごとにそのroleを引き受け、認証情報の期限が近づいたら引き受け直す。
