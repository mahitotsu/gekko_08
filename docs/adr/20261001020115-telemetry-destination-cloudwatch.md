# ADR: トレースはOTLPで出し、収集先はCloudWatchにする。メトリクスは出さず、件数や時間はログから集計する

## Status

Accepted (2026-10-01)。同日に改訂：メトリクスは出さないことにした（決定の2・3）。

## Context

各ホップの処理を、元のユーザーとリクエストに結びつけて追跡できること（FR-6）と、ホップごとの追加時間を実測して公開すること（NFR-3）を、
標準の形式で出すトレースとメトリクスで強化する。今は、各ホップがJSONのログに`requestId`と時間の内訳を書き、シナリオテストがそれを集めている。

出力の形式は、OpenTelemetry（OTLP）にする。エージェントのフレームワーク（Strands Agents、Claude Agent SDK）もOTelで出力するので、
同じ形式にそろえれば、ホップのスパンとフレームワークのスパンを1つのトレースにつなげられる。

決めるのは、その出力をどこに集めるかである。要件は次のとおり。

- サーバーレスとマネージドサービスを最大限に使い、コストと運用負荷を下げる（NFR-1）。
- 常駐コンポーネントを持たない（NFR-2）。
- 利用者が`cdk deploy`で自分のアカウントに再現できる（NFR-4）。
- 認証情報を、ログ・トレース・エージェントのLLMのコンテキストに入れない（SR-3）。

## Decision

**トレースはOTLPで出し、収集先はAmazon CloudWatchにする。メトリクスは出さず、認可の判定の件数や処理時間は、構造化ログから集計する。**

1. トレースは、X-RayのOTLPエンドポイントに送り、CloudWatchのTransaction Searchで見る。
2. メトリクスは出さない。各ホップの構造化ログには、受信の検証の結果（許可・拒否と拒否の理由）、呼び出し元、目的、scope、ステータス、
   処理時間の内訳がすでにあり、CloudWatch Logs Insightsで件数や時間を集計できる。メトリクスを送る時間も、系列の数の管理も要らない。
3. ログは、OTLPでは送らず、Lambdaの関数のログとしてCloudWatch Logsに出す。ログの形式はJSONにし、1件を1行のJSONで書く。
   トレースIDをログにも入れ、ログとトレースを行き来できるようにする。
4. 送り先は設定で差し替えられるようにする。利用者が他の収集先を使う場合は、送り先のOTLPエンドポイントを変えればよい。

Lambdaからの送り方（ADOTのLambdaレイヤーか、SDKから署名付きで直接送るか）は、このADRでは決めない。コールドスタートと、
関数の終わりに送り切る時間を実測してから決める。

## 採用しなかった選択肢

- **Amazon Managed Service for Prometheus**：OTelのメトリクスの標準的な送り先だが、トレースは扱わないので、トレースには別の送り先が要る。
  見るためのGrafanaも要り、Amazon Managed Grafanaは利用者ごとの固定費がかかる。
- **自前で運用する収集基盤（Jaeger、Tempo、Grafanaなど）**：ベンダーに依存しないが、常駐コンポーネントを持たないという要件（NFR-2）に反する。
- **外部のSaaS（Datadog、Honeycombなど）**：参照実装の既定にはしない。データがAWSの外に出て、利用者ごとに契約が要る。
  OTLPで出しておけば、利用者が送り先を差し替えられる（決定の4）。

## Consequences

### よくなること

- 常駐するものも固定費もなく、使った分だけの費用で済む。ログもトレースもCloudWatchの1か所で見られる。
- ホップのスパンとエージェントのフレームワークのスパンが、同じ形式で1つのトレースにつながる。
- OTLPなので、収集先を変えても計装は変わらない。

### 引き受けること

- **Transaction Searchの有効化はアカウント全体の設定になる**。IAMのアウトバウンドIDフェデレーションと同じく、参照実装は自動では有効にせず、
  前提条件としてREADMEに書く。
- **費用はスパンの量に比例する**。スパンはCloudWatch Logsとして取り込まれる。検証のときに、1リクエストあたりのスパンの数と大きさを見積もる。
- **件数や時間は、照会のたびにログから集計する**。常に見張る（アラームを出す）には、ログのメトリクスフィルターなどを利用者が加える。
- **トレースは、ログより広い範囲の人が見る**。スパンの属性に入れる値（subject、エージェントのメッセージの本文、ツールの引数と結果）を
  決めて制限する必要がある（SR-3）。
