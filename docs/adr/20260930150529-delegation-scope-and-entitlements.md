# ADR: 委任の範囲（scope）と業務的なアクセス権を分け、scopeはSTSとIAMに強制させ、業務的なアクセス権は属性サービスから得る

## Status

Accepted (2026-10-01)。要件定義は下の「要件への影響」のとおりに修正した。

## Context

[多段伝播のADR](20260930064314-multi-hop-authorization-context-propagation.md)では、ユーザーの識別子と業務属性（`branch`）を
SourceIdentityとtransitive session tagでログイン時に刻み、JWTで各ホップへ届けることにした。各ホップはJWTの`branch`とデータの`branch`を比べる。
OAuthのscopeに相当するもの（ユーザーの代理として何を許すか）は明示的には持たず、入口のIAM（actor）と、受信側がactorごとに許す操作で代えている
（当時の設計ガイド§3。今の設計ガイドでは[§3](../guide.md#3-各判断の根拠)）。

この構成には2つの弱さがある。

- **業務データをトークンに入れている。** 業務的なアクセス権の根拠（所属、役職、権限マスタ）は、本来は人事システムなど業務のデータ源が持つ。
  トークンに入れると、変更（異動、権限の剥奪）がトークンの更新まで効かず、セッションタグの制約（最大50個、値は単一の文字列）に収まる
  権限しか表せない。
- **委任の範囲が下流に届かない。** 同じユーザーの要求でも、「画面で案件の要約を見る」と「エージェントに分析させる」では、許すべき範囲が違う。
  今の構成では、元の取引の目的が下流に届かず、受信側はactorから推測するしかない。

### 事例と標準

| 出典 | scope（相当）の役割 | 業務的なアクセス権 |
|---|---|---|
| Microsoft Entra ID（委任された権限） | アプリがユーザーの代理で何をしてよいか | ユーザー自身の権限。実効権限は両者の積集合 |
| Curity、OWASPのマイクロサービスの指針 | 入口での粗い境界 | APIが業務ルールで細かく判定する |
| RFC 8693 Token Exchange | ホップごとの絞り込み（downscoping）。actは委任を見えるようにするが、制限するのは絞ったscope | 仕様の範囲外 |
| Transaction Tokens（IETF草案12、2026-08） | 取引の目的をできるだけ狭く定め、呼び出しの連鎖の中で変えない。外向けの粗いscopeとは意図的に分ける | 各ワークロードに任せる |
| Netflix Passport | 身元と属性だけを運ぶ | 各サービスが判定する |
| Google Zanzibar、Airbnb Himeji | トークンに権限を入れない | 中央の認可サービスが関係データから判定する |
| AWSのCedarによるマルチエージェントの事例（2026-07） | Token Exchangeで委任したタスクの範囲に絞る | ユーザーの属性とエンティティストアの属性でCedarが判定する |

scopeが答えるのは「このユーザーの代理として、この取引で、この呼び出し元に何を許すか」、業務的なアクセス権が答えるのは
「このユーザーはこのデータを扱ってよいか」で、両方を満たすときだけ許すのが共通の考え方である。

### 実機検証

[scope相当の値をSTSとIAMに強制させる](../../experiments/scope-tags/RESULTS.md)で、次のことを確かめた。

- **取引の目的**：目的をtransitive session tagとして刻める。刻める値はIAMで限れ、下流で上書きできない。目的によって、下流が発行できる
  JWTの宛先をIAMで変えられる（Transaction Tokensの目的に相当）。
- **ホップごとのscope**：`GetWebIdentityToken`の`Tags`はJWTの`request_tags`に入る。付けられる値を、宛先ごとにIAMで限れる
  （Token Exchangeのdownscopingに相当）。
- 目的を刻むchainの追加は、ローカルからの計測で中央値約120ms（Lambdaの中ではこれより短い見込み）。

## Decision

**認可の根拠を3つの層に分ける。委任の範囲（scope）はSTSとIAMに強制させてトークンで運び、業務的なアクセス権はトークンに入れず、
権威あるデータ源を持つ属性サービスから判定のときに得る。判定は、委任の範囲と業務的なアクセス権の両方が許すときだけ許す。**

| 層 | 問い | 担い手 |
|---|---|---|
| 1. 身元 | 誰の代理か、どのサービスから来たか、自分宛てか | 今のまま：SourceIdentity、入口のIAM（実行roleと関数）、JWTの`sub`と`aud` |
| 2. 委任の範囲 | この取引で、この呼び出し元に何を許すか | 取引の目的（transitive session tag `purpose`）と、ホップごとのscope（JWTの`request_tags`の`scope`） |
| 3. 業務的なアクセス権 | このユーザーは、このデータを扱ってよいか | 属性サービス（人事データ、権限マスタ） |

1. **取引の目的**：bffは、画面の操作（経路）ごとに目的を決め、federated roleのセッションから目的用のroleへchainして、`purpose`を
   transitive session tagとして刻む。刻める値はIAMで限る。途中のホップは目的を変えられない。目的に合わない下流のJWTは、IAMが発行させない。
2. **ホップごとのscope**：`allowCaller`で、呼び出し元がその宛先に付けられるscopeを宣言する。IAMは宣言した値しか付けさせない。
   受信側は、scopeのないJWTを「何も許さない」と扱う。
3. **業務的なアクセス権**：属性サービスをホップとして置き、人事データ（所属、役職）と権限マスタを持たせる。属性サービスは、
   **JWTのsubject本人のアクセス権だけを返し、照会する相手を引数に取らない**。誘導されたエージェントや侵害されたホップが、他人のアクセス権を
   問い合わせることはできない。
4. **トークンから業務属性を外す**：Pre Token GenerationはSourceIdentityだけを刻み、`branch`はトークンに入れない。
5. **判定**：受信側の共通部品が、身元と委任の範囲（目的、scope、actor）を検証して業務のコードに渡す。業務のコードは、委任の範囲が
   操作を許し、かつ属性サービスから得たアクセス権がデータを許すときだけ許す。

## 採用しなかった選択肢

- **業務属性をトークンに入れたままにする（今の構成）**：構成が単純で、判定のたびの問い合わせがない。変更がトークンの更新まで効かず、
  セッションタグの制約に収まる権限しか表せない。業務のデータ源とIdPを結びつける必要もある。
- **認可サーバーでToken Exchangeを行う**：scopeの絞り込みを1か所に集められる標準の方式だが、常駐コンポーネントを持たないという要件に反する。
- **Amazon Verified Permissions（Cedar）をPDPにする**：マネージドなPDPで、ポリシーを1か所で管理できる。参照実装の主題
  （委任の範囲をAWSに強制させること）から見ると追加の要素になり、ポリシー言語と判定ごとの費用が加わる。業務的なアクセス権の判定を
  外に出したくなったときの選択肢として、設計ガイドに書く。
- **関係ベースの中央認可サービス（Zanzibar型）**：大規模な共有モデルには向くが、参照実装の規模に対して過大である。
- **取引の目的だけ、またはホップごとのscopeだけにする**：目的だけでは、同じ取引の中でホップごとに範囲を絞れない。scopeだけでは、
  各ホップが付けるscopeが元の取引の目的に沿っているかを強制できない（各ホップは新しいJWTを作るため）。両方を使う。

## Consequences

### よくなること

- scopeの役割（委任の範囲）と業務データの役割（アクセス権）が分かれ、それぞれを標準の考え方どおりに説明できる。
- 委任の範囲は、アプリのコードではなくIAMのポリシーが強制する。目的に合わない下流への呼び出しは、アプリの判定より前に止まる。
- 業務的なアクセス権の変更（異動、権限の剥奪）が、次のリクエストから効く。セッションタグの制約に縛られない権限を表せる。
- デモで、目的による制限（例：エージェントによる分析では口座の残高を取らせない）と、業務データによる制限（例：他の支店、異動）を分けて示せる。

### 引き受けること

- **レイテンシが増える**：bffで目的を刻むchainが1回、判定するホップごとに属性サービスの呼び出しが1回加わる。
- **構成要素が増える**：属性サービス（ホップ）、人事データと権限マスタのテーブル、目的用のrole。
- **属性サービスが重要な構成要素になる**：業務的なアクセス権の根拠を一手に持つ。書き換えの権限と監査を守る必要がある。
- **委任の範囲の設計が必要になる**：目的とscopeの値、目的ごとに許す下流、宛先ごとに許すscopeを、CDKの宣言として設計する。
- **受信側の規律**：scopeのないJWTを「何も許さない」と扱う。属性サービスが使えないときは拒否する（fail closed）。
- **多段伝播のADRの一部を置き換える**：業務属性をtransitive session tagで運ぶ部分は、この決定で取引の目的を運ぶことに置き換わる。
  [IdPのADR](20260930091026-idp-cognito-user-pool.md)の、業務属性をIDトークンの`tags`に入れる部分も置き換わる。
  chain用roleの`sts:TagSession`で許すキーは`branch`から`purpose`に変わる。

## 要件への影響（2026-10-01に修正済み）

| 要件 | 修正前 | 修正後 |
|---|---|---|
| FR-1 | (a) 誰の代理か（ユーザーの識別子と業務属性）、(b) どのサービスから来たか、(c) 自分宛てか | (a) 誰の代理か（ユーザーの識別子）、(b) どのサービスから来たか、(c) 自分宛てか、**(d) 委任の範囲（この取引の目的と、呼び出し元に許された操作）** |
| FR-2 | 認可判定は、各ホップのアプリが検証済みの値だけを使って行う（ABAC）。自己申告は使わない | 認可判定は、各ホップのアプリが、**検証済みの委任の範囲と、権威あるデータ源から得た業務的なアクセス権の両方**を使って行う。自己申告は使わない |
| FR-3 | ユーザーの識別子と業務属性はログイン時に一度だけ確定し、途中のホップ（AIエージェントを含む）は変更できない | ユーザーの識別子と取引の目的は入口で確定し、途中のホップ（AIエージェントを含む）は**変更も拡大もできない**。業務的なアクセス権は権威あるデータ源から得て、途中のホップは変更できない |
| FR-8（新規） | — | 業務的なアクセス権の変更（異動など）は、次のリクエストから反映される |
| FR-7 | エージェントのシナリオとプロンプトインジェクションの拒否 | 加えて、取引の目的による制限と、業務的なアクセス権の変更の反映を示す |
| スコープ外 | ホップごとに`scope`を絞る仕組み（代理で何を許すかは、呼び出し元のサービスを確かめた受信側が判断する） | **削除する**（この決定で扱う） |
