# ADR: 委任の範囲の定義を提供側と利用側に分け、取引の目的は影響の大きいscopeの発行を限るためだけに使う

## Status

Accepted (2026-10-01)。[委任の範囲のADR](20260930150529-delegation-scope-and-entitlements.md)の決定1のうち「目的に合わない下流のJWTは、
IAMが発行させない」（すべての組を目的で限る部分）、決定2（呼び出し元と呼び出し先の組ごとに1つのscopeを宣言する）、決定5のうち業務のコードに目的を渡す部分を置き換える。

## Context

委任の範囲のADRは、委任の範囲を取引の目的（transitive session tag `purpose`）とホップごとのscope（JWTの`request_tags`の`scope`）で表し、
どちらもSTSとIAMに強制させることにした。今の実装には、次の問題がある。

1. **同じ組で、目的によって許す操作を変えられない**。`Hop#allowCaller`は、組ごとにscopeを1つと、JWTを発行できる目的の一覧を宣言する。
   IAMは、JWTの発行（`sts:GetWebIdentityToken`）を目的で、scopeを付けること（`sts:TagGetWebIdentityToken`）をscopeの値で、別々に判定する。
   同じ組に2つのscopeを許すと、どの目的の取引でも両方を付けられる。
2. **定義のオーナーがいない**。すべての組を、1か所（`app-stack.ts`）で、呼び出し先の側から宣言している。実際の組織では、APIを提供する側が
   利用者をすべて把握する必要があり、利用者が増えるたびに提供側の変更が要る。
3. **目的の追加と削除が、すべてのサービスに及ぶ**。すべての組を目的で限るので、目的を1つ増やすと、その取引が通る経路のすべての組の宣言を変える必要がある。
   業務のコードが目的を見る場合は、コードの変更も要る。

一方で、目的には、scopeと呼び出し元（actor）では代えられない役割がある。scopeとactorが効くのは1ホップ分だけで、受信側は「直前の呼び出し元が誰で、
自分に何を許したか」までしかわからない。複数の経路が共有するホップが侵害されると、経路をまたいで権限を持ち出せる。

> 例：case-serviceは、エージェントの経路（fraud-mcp → case-service）と、人間が凍結を解除する経路（bff → case-service → account-service）の両方にある。
> case-service → account-serviceに解除のscopeを許していると、目的がなければ、乗っ取られたcase-serviceは、エージェントの取引の最中に解除のJWTを発行できる。
> 目的があれば、その取引の目的は途中で変えられないので、IAMが止める。

[検証](../../experiments/scope-tags/RESULTS.md)のE4で、`sts:TagGetWebIdentityToken`の許可にも`aws:PrincipalTag/purpose`の条件が効き、
同じ組で、目的ごとに付けられるscopeを変えられることを確かめた。

## Decision

**委任の範囲の定義を、目的の一覧・提供側の定義・利用側の定義の3つに分け、合成のときに突き合わせてIAMと共通部品の設定を生成する。
取引の目的は、影響の大きいscopeのJWTの発行を限るためだけに使い、業務のコードは目的を使わない。**

1. **3つの定義とオーナー**

   | 定義 | オーナー | 書くこと |
   |---|---|---|
   | 目的の一覧 | 入口（bff） | 取引の種類（少数に保つ）と、経路ごとの目的 |
   | 提供側の定義 | APIを提供するサービス | 提供するscopeの一覧。影響の大きいscopeには、使ってよい目的と、必要なら使ってよい呼び出し元 |
   | 利用側の定義 | APIを使うサービス | 呼び出し先ごとに、付けたいscopeの一覧 |

   提供側は、普通のscopeについては利用者を知らなくてよい。影響の大きいscopeについてだけ、目的と呼び出し元で限れる。
2. **突き合わせ**：合成のときに、利用側が求めるscopeが提供側にあること、影響の大きいscopeでは利用側が許された呼び出し元であること、
   提供側が名指しする目的が目的の一覧にあることを確かめる。整合しなければ合成を失敗させる。
3. **IAM**：利用側のchain用role（bffでは目的用のrole）に、呼び出し先ごとに次の文を生成する。
   - `sts:GetWebIdentityToken`：宛先の`ForAllValues`＋`Null`、ES384、300秒以下。目的の条件は付けない。
   - `sts:TagGetWebIdentityToken`（普通のscope）：宛先の`ForAllValues`＋`Null`、tagのキーは`scope`だけ、`aws:RequestTag/scope`＝付けてよい普通のscopeのどれか。
   - `sts:TagGetWebIdentityToken`（影響の大きいscopeごとに1つ）：上に加えて、`aws:PrincipalTag/purpose`＝提供側が許した目的のどれか。

   入口のresource policyと`sub`の対応表は、その呼び出し先を求めた利用側の定義から生成する。目的の一覧から、目的用のroleの信頼ポリシー（刻める目的）を生成する。
4. **scopeの選び方**：業務のコードは、呼び出しごとに必要なscopeを指定する（呼び出し先に1つしか求めていなければ省略できる）。JWTに付けるscopeは1つ。
   共通部品は、利用側の定義にないscopeならSTSを呼ばずに失敗させる。目的に合わない影響の大きいscopeは、IAMが拒否する。
5. **業務のコードは目的を使わない**：共通部品は、目的を検証してログとトレースに出すが、業務のコードには渡さない。業務のコードが判断に使う委任の範囲は、
   scopeだけである。目的で振る舞いを変えたいときは、scopeを分け、どの目的で使えるかを提供側の定義に書く。目的を使ってよいのは、入口（刻む）、IAM（発行を限る）、
   共通部品（受信時の照合）、追跡（ログ、トレース、監査）だけである。
6. **受信時の照合**：受信側の共通部品は、届いたJWTのscopeが提供側の定義にあること、影響の大きいscopeなら目的が許した目的であることを確かめる。
   IAMの設定の誤りや手での変更があっても、提供側の定義で止める。目的やscopeのないJWTは、今のとおり拒否する。
7. **回帰テスト**：`Hop`のテンプレートの単体テストで、影響の大きいscopeの文に目的の条件があること、普通のscopeの文に影響の大きいscopeが混ざらないことを確かめ、
   壊すとテストが失敗することを確かめる。突き合わせ（2）の誤りが合成の失敗になることも確かめる。

## 採用しなかった選択肢

- **目的をなくし、scopeとactorだけにする**：Contextのとおり、共有のホップが侵害されたときに、経路をまたいだ権限の持ち出しを止められない。
  FR-3（目的は入口で確定し、途中で変更も拡大もできない）とFR-7（エージェントのホップが侵害されても実行できない）を満たせない。
- **入口で、取引で許す操作の上限（scopeの一覧）を刻む**：目的と同じく経路の奥まで運べるが、入口がすべての下流のscopeを知る必要があり、目的より結合が強い。
  tagの値の長さ（256文字）にも制約がある。
- **すべてのscopeを目的に縛る**：目的の追加と削除が、すべてのサービスの定義に及ぶ。
- **発行は緩く、受信側の業務のコードが目的とscopeの組み合わせを確かめる**：組み合わせの判断が各サービスのコードに散らばり、1つの漏れが気づきにくい穴になる。
  この参照実装の主張（委任の範囲はSTSとIAMに強制させる）とも合わない。
- **呼び出し先の側で、すべての呼び出し元を宣言する（今の形）**：提供側が利用者をすべて把握する必要があり、運用が回らない。
- **共通部品が目的からscopeを選ぶ**：目的に縛らない普通のscopeが同じ組に複数あると選べない。業務のコードが操作に応じて指定するほうが、OAuthのToken Exchangeで
  要求するscopeを指定するのと同じ形で、自然である。
- **1つのJWTに複数のscopeを付ける（空白区切りの一覧）**：1回の呼び出しは受信側の1つの操作で、判断に要るscopeは1つである。
  1回の呼び出しで複数の操作を行う場合は、その操作に1つのscopeを定義する。

## Consequences

### よくなること

- 同じ組で、取引によって許す操作を変えられる。影響の大きい操作は、許した目的の取引でだけ、IAMがJWTを発行させる。
- 共有のホップが侵害されても、経路をまたいで影響の大きい操作を持ち出せない。
- 目的の追加と削除の影響が、目的の一覧、入口、影響の大きいscopeの提供側の定義に限られる。業務のコードには及ばない。
- 提供側は、普通のscopeの利用者を把握しなくてよい。定義のオーナーが明確になる。

### 引き受けること

- **普通のscopeは、どの取引でも、許された組なら発行される**。今の「目的に合わない組ではJWTそのものを発行させない」という効き方はなくなる。
  目的で止めたい操作は、scopeを分けて影響の大きいscopeとして宣言する必要がある。どれを影響の大きいscopeにするかは、提供側の判断になる。
- **利用側の定義は、実質的に呼び出しの許可になる**。普通のscopeについては、利用側が書けば呼べるようになる。利用側の定義の変更は、提供側
  （またはセキュリティの担当）がレビューする運用が要る。
- **定義の共有が要る**。参照実装は単一のCDKアプリなので、合成の中で突き合わせられる。複数のリポジトリやアカウントに分かれる場合は、定義を共有する場所が要る。
- **`allowCaller`と共通部品の呼び出しの形が変わる**。参照実装を当てはめた利用者は、宣言と呼び出しを書き換える。
