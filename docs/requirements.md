# 要件定義

参照実装を設計する前提となる要件をまとめる。各要件の出どころを示す。

- **明言**：プロジェクトオーナーが明示した要件
- **会話で決定**：検証や議論の中で合意した要件
- **推奨採用**：選択肢を示し、推奨どおりに決めた要件（2026-09-30）

関連文書：[PRFAQ](prfaq/aws-authorization-context-propagation.md)、[多段伝播のADR](adr/20260930064314-multi-hop-authorization-context-propagation.md)、
[入口のADR](adr/20260930083437-entry-via-bff.md)

## 目的と対象

- AWS上でマイクロサービスを実装するエンジニアに向けて、Authorization ContextとWorkload Identityを分離し、
  「誰の権限で処理するのか」を多段呼び出しの奥まで届ける仕組みの参照実装（OSSのCDK構成と設計ガイド）を提供する。（明言）
- 事業化はしない。サポートやSLAは提供しない。（明言）

## 機能要件

| ID | 要件 | 出どころ |
|---|---|---|
| FR-1 | 各ホップは、受け取ったリクエストについて次の3つを確かめられる。(a) 誰の代理か（ユーザーの識別子と業務属性）、(b) どのサービスから来たか、(c) 自分宛てか。OAuth Token Exchangeと同等のことを実現する | 明言 |
| FR-2 | 認可判定は、各ホップのアプリが検証済みの値だけを使って行う（ABAC）。ヘッダー・引数・自然言語による自己申告は使わない | 会話で決定 |
| FR-3 | ユーザーの識別子と業務属性はログイン時に一度だけ確定し、途中のホップ（AIエージェントを含む）は変更できない | 明言（「Authorization Contextはcallerに作らせない」） |
| FR-4 | 途中のホップを飛ばして、その先のホップを呼ぶことはできない | 会話で決定 |
| FR-5 | ログインにはAmazon Cognito User Poolを使う。入口はBFFとし、ブラウザなどのパブリッククライアントには認証情報（Cognitoのトークン、AWSの認証情報）を持たせない | 明言 |
| FR-6 | 各ホップのデータへのアクセスは、そのホップ自身の実行roleで行う。ユーザーとしてAWSリソースにアクセスすることは要件としない | 明言 |
| FR-7 | 各ホップのログとCloudTrailで、処理を元のユーザーとリクエストに結びつけて追跡できる | 推奨採用 |
| FR-8 | デモとして、同期のマイクロサービスの多段呼び出しに加えて、AIエージェント→MCPサーバー→内部サービスのシナリオを含める。プロンプトインジェクションで誘導されたエージェントの要求が拒否されることを示す | 推奨採用 |

## 非機能要件

| ID | 要件 | 出どころ |
|---|---|---|
| NFR-1 | サーバーレスとマネージドサービスを最大限に使い、コストと運用負荷を下げる | 明言 |
| NFR-2 | 認可サーバー、SPIRE、サイドカーなどの常駐コンポーネントを持たない | 会話で決定（PRFAQ） |
| NFR-3 | レイテンシの目標値は置かない。ホップごとの追加時間を実測して公開する | 推奨採用 |
| NFR-4 | 利用者が`cdk deploy`で自分のAWSアカウントに再現できる | 会話で決定（PRFAQ） |

## セキュリティ要件

| ID | 要件 | 出どころ |
|---|---|---|
| SR-1 | ホップ間で受け渡す認証情報が漏れても、それだけではどのホップも呼べない | 会話で決定 |
| SR-2 | 同じアカウント内の他の主体（広い権限を持つものを含む）が、許可されていないホップを呼べない | 会話で決定（検証で判明） |
| SR-3 | 認証情報を、ログ・トレース・エージェントのLLMのコンテキストに入れない | 会話で決定 |

## 前提と範囲

| 項目 | 初版の範囲 | 出どころ |
|---|---|---|
| 呼び出し方式 | 同期呼び出し（Lambda Function URL）だけ | 推奨採用 |
| 処理時間 | 1回のリクエストの処理は、各ホップでLambdaの上限（15分）以内に収まる。長い対話は複数のリクエストとして扱う | 推奨採用 |
| アカウント | 単一のAWSアカウント | 推奨採用 |
| 連携先 | AWS内部のホップ間だけ。AWSの外のサービスにユーザーの証明を渡すことは扱わない | 推奨採用 |
| コンピュート | AWS Lambda | 会話で決定（PRFAQ） |
| IdP | Amazon Cognito User Pool（Pre Token Generation V2トリガー） | 会話で決定（PRFAQ） |

## 将来の拡張（初版では扱わない）

- 非同期処理（SQS・EventBridgeなど）を挟む呼び出し
- 複数のAWSアカウントにまたがる構成
- AWSの外のサービスへのユーザーの証明の受け渡し（AgentCore Identityなど既存の手段との使い分けを含む）
- Lambda以外のコンピュート、Cognito以外のIdP

## スコープ外

- 業務RBACの持たせ方の一般論（参照実装では1つの例を示すにとどめる）
- Pre Token Generation V1トリガー
- ホップごとに`scope`を絞る仕組み（推奨採用）。受信側は呼び出し元のサービスをIAMで直接確かめられるので、
  「このサービスからaliceの代理で来たリクエストに何を許すか」を受信側のABACで決める。
  代理で許す範囲の判断は、Token Exchangeのように認可サーバーへ一元化されず、各受信側に分散する。この違いは設計ガイドに明記する

## 設計で決める事項

要件ではなく、設計の中で決める事項。

- BFFのホスティング（Lambda Function URL、API Gateway、CloudFrontとの組み合わせなど）
- BFFのセッションとトークンの保存先と暗号化、ログインフロー（Authorization Code＋PKCE）とクライアントシークレットの扱い
- `AssumeRoleWithWebIdentity`をリクエストごとに呼ぶか、IDトークンの有効期限の範囲で再利用するか
- レイテンシの最適化（STSクライアントの使い回し、JWKSのキャッシュ）とJWTの有効期限
- CDK Constructの単位と、JWT検証・ABACの共通部品
- デモのエージェントに使うモデルとMCPサーバーの構成
