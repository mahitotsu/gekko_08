# 検証結果：入口のIAMで拒否された呼び出しは、関数のログに残るか

実施：2026-10-03（UTC）、ap-northeast-1。デプロイ済みのスタック`Gekko08App`に対し、シナリオテストの補助関数（`tests/scenario/helpers.ts`）で呼んだ。
検証のための構成は作っていない。

目的：入口のresource policyで拒否された呼び出し（許可していない主体からの呼び出し）が、関数のログに残るかを確かめる。
攻撃の試みを、関数のログから追えるかにかかわる。

## 結論

**入口のIAMで拒否された呼び出しは、関数のログに何も残らなかった。** 関数そのものが起動しないので、業務のログも、Lambdaが起動のたびに書く記録も出ない。
入口で拒否された試みを追うには、CloudTrailでLambdaのデータイベント（`InvokeFunctionUrl`など）を記録する必要がある。

## 手順と観測

1. bffと同じ手順で目的を刻んだセッションを作り、case-service宛ての正しいJWTを発行した。
2. テストを実行する主体（case-serviceを呼ぶことを許可していない主体）の認証情報で署名し、そのJWTと、識別できるリクエストID（`h4-probe-<時刻>`）を付けて、
   case-serviceのFunction URLを3回呼んだ。3回とも403だった。
3. 2分待ってから、case-serviceのロググループを、呼び出しの直前からの範囲で読んだ。

| 読んだもの | 結果 |
|---|---|
| リクエストIDを含む行 | 0行 |
| その時間帯のすべての行（Lambdaの起動と終了の記録を含む） | 0行 |
| 直前の6時間のすべての行（ロググループが動いていることの確認） | 19行 |

## 設計への示唆

- 共通部品の`rejected`のログに出るのは、入口のIAMを通ったあとに共通部品が拒否した呼び出しだけである（設計ガイド§6の記述と一致する）。
- 許可していない主体からの試みを常に記録したい場合は、CloudTrailのLambdaのデータイベントを有効にする。呼び出しの数に比例して費用がかかるので、参照実装では有効にしない。
