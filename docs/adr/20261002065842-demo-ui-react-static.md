# ADR: デモの画面はReactの静的なSPAにし、合成のときにビルドする

## Status

Accepted (2026-10-02)。[BFFの公開とセッションのADR](20260930093744-bff-hosting-and-session.md)の配信の形（CloudFrontの既定はS3、`/api/*`はbff）は変えない。

## Context

デモの画面は、操作の結果をステータスコードとJSONのまま表示していた。記事やREADMEで画面を見せるとき、デモで示したいこと
（FR-7。取引の目的、どの層が拒否したか、誘導されたエージェントの解除の試みが拒否されること）が、JSONを読み解かないと伝わらない。

表示を増やすと、素のHTMLとJavaScriptでは、画面の部品と状態の扱いが読みにくくなる。一方で、画面は認可の仕組みの一部ではなく、
FR-5（ブラウザに認証情報を持たせない）とNFR-4（`cdk deploy`で再現できる）を崩してはならない。

## Decision

**画面はReact（TypeScript）とViteで作る静的なSPAにする。CDKの合成のときに開発機でビルドし、今と同じくS3からCloudFrontで配信する。
サーバー側の描画（SSR）は使わない。**

1. `web/`をnpmのワークスペース（`@gekko08/web`）にする。`WebFrontend`は、`Source.asset`のローカルのバンドルで`vite build`を実行し、
   出力だけをS3に置く。Dockerは使わない。
2. 画面は、操作ごとに、bffが刻んだ取引の目的、リクエストID、結果（許可・拒否）、拒否したときはその層（委任の範囲、業務的なアクセス権）を表示する。
   エージェントの分析では、ツールの呼び出しを時系列に並べ、拒否されたものに理由を付ける。応答のJSONは折りたたんで残す。
3. 画面は、ユーザーや役職に応じて操作を隠さない。拒否されるところを見せるのがデモである。判定はすべて各ホップが行い、画面の対応表（理由→層）は表示にだけ使う。
4. 表示のために、bffは最初のホップを呼ぶ経路の応答に`purpose`を加える。fraud-agentは、`toolCalls`の各要素に、呼び出し先のホップが返した拒否の理由（`reason`）を加える。
   理由はホップのコードが決める固定の文字列で、モデルが作る値ではない。ログに出す項目は変えない（ツール名とステータスだけ）。

## 採用しなかった選択肢

- **素のHTMLとJavaScriptのまま**：ビルドが要らないが、表示を増やすと部品と状態の扱いが読みにくくなる。
- **Next.jsやNuxtのSSR**：描画のためのサーバー（Lambdaなど）が、ブラウザとbffの間に入る。そのサーバーはセッションcookieを中継する要素になるが、
  ホップの仕組み（実行roleとJWT）の外にあり、§5の侵害の整理に要素が1つ増える。デモの画面にその価値はない。
- **Next.jsやNuxtの静的な書き出し**：配信の形は採用した案と同じになるが、使わない機能（ルーティング、サーバーの描画）を持ち込む。
- **Vue**：採用した案と同等にできる。読者の層の広さでReactを選んだ。

## 結果として引き受けること

- 合成のときに、`web/`の依存（React、Vite）が開発機に入っている必要がある（`npm install`で入る）。合成の時間がビルドの分だけ延びる（数百ミリ秒）。
- 画面のJavaScriptは、圧縮後で約75KBになる。
- bffとfraud-agentの応答が表示用の項目で増える。シナリオテストは、この項目に依存しない。
