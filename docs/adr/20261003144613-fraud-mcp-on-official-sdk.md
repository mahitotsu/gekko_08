# ADR: MCPサーバー（fraud-mcp）は、MCPの公式SDK（v2）で実装する

## 状態

提案（2026-10-03）。単体テストで、2025年の版のリクエストに応えることを確かめた。デプロイしてシナリオテスト（エージェントの経路）が通れば、採用にする。

## 背景

fraud-mcpは、MCPのJSON-RPCを自前で処理していた。実装した時点の公式SDK（`@modelcontextprotocol/sdk` 1.31）が、
プロトコルの`2026-07-28`版に対応していなかったためである（[エージェントのフレームワークの検証](../../experiments/agent-frameworks/RESULTS.md)）。

その後、SDKのv2（`@modelcontextprotocol/server`）が安定版になり、`2026-07-28`版を実装した。参照実装は、利用者が自分のMCPサーバーに
当てはめる手本でもある。プロトコルの処理（版の交渉、入力の検証、エラーの形）を自前で持つと、仕様の改訂に追従し続ける必要があり、手本としても適さない。

## 決定

**fraud-mcpは、MCPの公式SDKのv2（`@modelcontextprotocol/server`）で実装する。**

- ツールは`McpServer`の`registerTool`で定義し、引数はzodのスキーマで検証する。スキーマに合わない引数では、業務のホップを呼ばない。
- ステートレスにする。1回の呼び出しごとにサーバーを作り、ツールは、その呼び出しで受け取った委任（共通部品の`call`）で業務のホップを呼ぶ。
- 2025年の版（`initialize`で始める版）は、`isLegacyRequest`で見分け、`WebStandardStreamableHTTPServerTransport`（セッションなし、JSONで応答）で応える。
  `2026-07-28`版は、`createMcpHandler`（`legacy: 'reject'`、`responseMode: 'json'`）で応える。どちらもSSEを使わない。
- 共通部品は、業務のコードに、受信したヘッダーを渡す。JWT、受け渡されたセッション、署名のヘッダーは除く（SR-3）。SDKがMCPのヘッダー
  （`mcp-protocol-version`、`2026-07-28`版の`mcp-method`など）を読むためである。
- 共通部品の中継（`startMcpRelay`）は、`mcp-`で始まるヘッダーをすべて転送する。

## 採用しなかった選択肢

- **自前のJSON-RPCの処理を続ける**：版の交渉と検証を自前で持ち続けることになる。手本として、利用者に同じことを求めることにもなる。
- **SDKのv1（1.x）**：`2026-07-28`版に対応しない。
- **`createMcpHandler`の既定（`legacy: 'stateless'`）**：2025年の版にSSEで応えるので、ホップの応答（JSONの本文）に収まらない。

## 結果として引き受けること

- **応じるプロトコルの版は、SDKが決める**。SDKを更新すると、応じる版も変わる。
- **送信側のMCPの部品は、v1の型のまま**：共通部品の`HopMcpTransport`は、v1のSDKの`Transport`を実装している（v1の`Client`を使うフレームワーク向け）。
  v2のクライアントへの対応は、使うフレームワークがv2に移ったときに行う。
- **新しい系列のSDKに頼る**：v2は2026年7月に出た新しい系列である。不具合があれば、版を固定して避ける。
- **エージェント（Claude Code）がどちらの版で話すかは、実機で確かめる**：中継はどちらの版のヘッダーも転送するので、どちらでも動く想定である。
